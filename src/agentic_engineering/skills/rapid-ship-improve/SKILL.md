# Improve rapid-ship

Turn a demonstrated gap into a small, reviewed framework PR. Keep the consuming project's work moving.

1. Record expected versus actual behavior, reproduction steps, and the installed devctl version. Separate project configuration from framework behavior. If existing project settings solve it, make the authorized local change and finish there. Start upstream work only for a demonstrated reusable gap. A reusable code, profile, or skill gap belongs in rapid-ship.
2. Find the framework source repository from installed package metadata or the user's selected fork; verify its remote and relevant version. The consuming project's origin is not the framework destination. Search existing framework Linear work and GitHub PRs before starting. Reuse matching work instead of duplicating it; report unavailable access without claiming synchronization.
3. Reduce evidence to a shareable reproduction. Replace private project data, names, paths, hostnames and credentials with synthetic fixtures. Inspect the actual diff and PR text before publishing; raw logs and private source stay local.
4. Work in a separate framework checkout and branch. Choose the highest practical enforcement rung: **1** structure/types, **2** automated checks, **3** guidance/agent review, **4** human style feedback. Reproduce the failure before changing behavior. For skills, test an agent's response before and after; for code, add a meaningful regression test. Preserve supported project languages, models, harnesses and environments.
5. Run relevant checks and obtain independent review of the change. Make any proposed change to checks, permissions or trust policy explicit in the PR; never weaken them merely to make a failure disappear. Recheck the final revision after fixes.
6. Use existing authorization to submit or update the framework PR when destination and access are established. An improvement/PR request needs no repeated permission; ordinary diagnosis alone does not authorize external posting. If publication is blocked, leave a concrete local draft and name the blocker.

Report according to what actually happened:

**Before any implementation or verification:** provide a proposal with `Destination`, `Existing work`, `Proposed change`, `Checks to run`, and `Review needed`. State: “No changes, tests or independent review performed.” Any PR body is a local proposal in future tense. Sanitation of a future fixture or diff belongs under `Checks to run`.

**After any implementation or verification, including partial progress before losing access:** report the actual PR URL or local status, duplicate search result, change, and verification. Each result names the command/reviewer and inspected artifact. Inspecting draft text does not verify a code diff. Include remaining blockers. Use existing authorization for the next step; do not end an authorized change with another permission request.

Submitting a PR does not merge it, replace the installed controller, switch an active run, or promote trust. Installation and approval remain separate reviewed decisions.
